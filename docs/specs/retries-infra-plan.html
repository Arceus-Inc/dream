SLICE 01

Wire CredentialPool into the live streamer

highest ROI
spec 02 §7–11 depends: credentials.toml or multi-key env tests exist for pool

Problem

CredentialPool + cooldown ladder shipped in Spec-02 stage 3, then the REPL consumer was deleted in wave-1. build_harness still builds FailoverStreamer([("primary", OpenAIChatStreamer(...))]) from a single api_key. pick_live / record_attempt are never called on a beat. Multi-key / cooldown is dead code on the live path.

Today

  • One env key FailoverStreamer retries the same streamer; rotation seam idle
  • Pool unit-tested tests/test_api/test_spec02_contracts.py
  • Auth 401/403 Rotates substrate name only — no next key in same substrate

Need

  • Pool owns key selection Before each attempt: pick_live() → build or swap client
  • Classify → record_attempt success / transient_exhausted / auth / hard_refusal
  • NoLiveCredential → FailoverPolicy.next Outer escalate only after pool empty

Target flow

1
Turn starts · active substrate
2
pick_live from that pool
3
stream (inner SDK / FailoverStreamer retries)
4
record_attempt · maybe bench key
5
if pool empty → next substrate

Implementation sketch

  1. Load pools at harness build — optional credentials.toml via load_credential_pools; if absent, synthesize a one-key pool from api_key so behavior stays backward compatible.
  2. Streamer factory per credential — either rebuild OpenAIChatStreamer with the picked key, or inject key into httpx_chat_completion_stream per attempt (prefer inject to avoid re-assembling system prompt).
  3. Bridge FailoverStreamer ↔ pool — on retryable exhaust: record_attempt(..., "transient_exhausted") then pick_live again before next_substrate. On 401/403: record_attempt(..., "auth") (benches key immediately per ladder).
  4. Events — emit existing Spec-02 events if hooks exist: substrate.credential.benched / restored / substrate.failover (from FailoverPolicy today).
  5. Tests — fake clock + two keys: first key 429 exhaust → bench → second key succeeds; both keys auth-fail → NoLiveSubstrate; single-key env path unchanged.

Out of scope for this slice

  • Hermes-style length-continue / compress-restart (slice 2)

Estimate: medium. Pool + ladder exist; risk is the streamer/key injection seam and not breaking single-key Azure e2e.
SLICE 02

Hermes-style classified one-shot recoveries

design-heavy
hermes error_classifier spec 02 + 04 overflow pairs well after slice 1

Problem

FailoverStreamer treats most failures as “same request, backoff, maybe rotate.” Hermes separates what happened from what to do: ClassifiedError carries retryable, should_compress, should_failover, etc. Blind retry on context overflow or 413 wastes the attempt budget and can failover away from a healthy key.

Minimal taxonomy (dream v1 — not full Hermes zoo)

Class Signals Action (one-shot)
rate_limit 429 + Retry-After Backoff (cap wait ≤60s à la OpenClaw) → retry same; then pool/failover
server_transient 408 / 5xx / transport Same as today: bounded retry → rotate
auth 401 / 403 Bench key (slice 1) / next substrate — no blind re-send
context_overflow PTL / known overflow body Compress / PTL path (already in loop) — do not failover
payload_too_large 413 One compress/shrink attempt; else hard fail
hard 400 (non-overflow), policy blocks Raise — no retry, no rotate

Implementation sketch

  1. New module — dream/api/error_classify.py (or engine/_error_classify.py): frozen ClassifiedError + classify(exc) -> ClassifiedError.
  2. FailoverStreamer uses classifier — replace status frozensets with action hints; keep mid-turn no-replay rule.
  3. Cap Retry-After — if provider asks for hours, fail/failover instead of sleeping (OpenClaw pattern).
  4. Wire overflow to existing PTL — classifier returns should_compress; streamer surfaces a typed signal the act-loop already understands (or re-raise a dedicated exception the loop catches). Avoid duplicating PTL logic inside the streamer.
  5. Tests — table-driven classify cases; streamer: 429 with huge Retry-After does not sleep hours; 413 does not call next_substrate.

Key files

src/dream/engine/_failover_streamer.py   # consume classifier
src/dream/engine/_loop.py                # PTL already here — handoff only
docs/existing_frameworks/hermes-agent-inspiration.md §4
docs/existing_frameworks/openclaw-inspiration.md (Retry-After cap)
Do not port Hermes’ full OAuth / thinking-signature / llama.cpp grammar strip zoo in v1. Keep a thin table; extend when a live failure proves the need.
Estimate: medium–large. Classifier itself is small; careful handoff to PTL and sleep-cap is where bugs hide.
SLICE 03

Heartbeat coma → failover (not only abort)

spec gap
spec 02 §14 spec 06.5 / 03 heartbeat needs 2+ substrates to matter

Problem

Spec 02: three consecutive health()=down during a long call should failover if a fallback is live, else abort. Today HeartbeatMonitor raises ComaDetected and the session cancels the turn — no attempt to rotate substrate or key.

Today

  • Monitor primitive Interval + threshold; pure — no session knowledge
  • Session cancels Coma → abort in-flight __anext__

Need

  • Policy at session/streamer On coma: if FailoverPolicy has next → rotate + retry turn boundary
  • Still abort when alone Single substrate / empty pool → keep ComaDetected abort

Implementation sketch

  1. Define health for live path — who implements health() today for Azure OpenAI? Likely a lightweight ping or “last chunk age”. Document and implement if missing.
  2. Coma handler in session / query engine — catch ComaDetected; ask FailoverPolicy / pool for alternate; if yes: emit substrate.failover, restart turn from boundary (same mid-turn rule: only if no events yielded, or always restart whole turn — prefer whole-turn restart for coma).
  3. Cap coma failovers — e.g. at most one failover per turn to avoid ping-pong.
  4. Tests — fake health: 3 downs with two streamers → second receives the turn; one streamer → ComaDetected still aborts.

Key files

src/dream/engine/_heartbeat.py
src/dream/engine/_engine.py / session orchestrator (coma cancel site)
src/dream/api/failover.py
docs/specs/divo/02-config-and-providers.md §14
docs/specs/divo/06p5-background-turns-and-heartbeat.md
Reality check: with today’s single Azure deployment this slice mostly changes abort semantics only when a second substrate exists. Ship after slice 1 if you want multi-key; otherwise it’s latent until a second provider is configured.
Estimate: medium. Monitor exists; hard part is turn-restart vs cancel semantics without duplicating half-yielded events.
SLICE 04

Enforce safe_retry / stop_condition in the act-loop

behavior change
spec 05 tool contract hermes tool_guardrails orthogonal to provider retry

Problem

Tools already emit structured recovery metadata. derive_observation lifts them into next_actions for the model. The engine does not stop a model that ignores stop_condition and retries the same failing call forever (until IterationBudget / max_turns). Hermes’ tool guardrails warn then halt on exact-failure / same-tool / no-progress streaks.

Two depths (pick one when implementing)

Depth Behavior Risk
4a · Circuit breaker Track (tool, args-hash, error) streaks. After N identical failures, inject a synthetic tool result or block further identical calls this turn. Low — Hermes-proven; no auto-retry inventing new args
4b · Engine auto-retry Parse safe_retry and re-dispatch without a model turn. High — hints are prose for the model; auto-exec is unsafe / ambiguous
Recommendation: implement 4a only. Do not auto-execute safe_retry strings. Treat this slice as loop safety, not provider resilience.

Implementation sketch (4a)

  1. Stateless controller — dream/engine/_tool_guardrails.py: observe each tool result; return ok | warn | block (Hermes shape).
  2. Defaults — exact same failure warn@2 block@5; same tool any-error warn@3 halt@8; config via SessionOptions / harness config (interactive vs autonomous).
  3. On block — return synthetic error ToolResult with clear stop text; optionally set a turn flag so the model must change strategy or end turn.
  4. Tests — five identical bash failures → sixth blocked; different args still allowed; mutating vs idempotent sets if we adopt Hermes’ frozensets.

Key files

src/dream/tools/builtin/_errors.py
src/dream/tools/_base.py                 # derive_observation
src/dream/engine/_tool_dispatch.py
src/dream/engine/_loop.py                # observe after each tool
chorus tools already emit the three-part contract
Estimate: medium for 4a. Small surface, high leverage for long beats that thrash one tool. Independent of slices 1–3.

Suggested order (not mandatory)

You pick. This is the dependency-aware default if you want “retries infra” to mean Spec-02 completion first.

Recommended path

  1. Slice 1 — CredentialPool on live path (unblocks multi-key reality)
  2. Slice 2 — thin classifier + Retry-After cap + overflow handoff
  3. Slice 3 — coma → failover (valuable once ≥2 substrates)
  4. Slice 4a — tool circuit breaker (anytime; parallel-safe)

Leave alone

  • ask_until_parsed / output_guard Already the right parse-layer retries
  • IterationBudget Turn accounting, not provider weather
  • Credential brokerage PRs Org secrets ≠ LLM key pool
  • Slice 4b auto-dispatch Skip unless a concrete product need appears
